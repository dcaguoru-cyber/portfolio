01 — Executive Summary

Executive Summary

DaveTraceTech is a cybersecurity and card-fraud prevention concept that originated in 2023 and has since evolved through academic study, prototype development, and innovation competition recognition at Kingston University. The project explores how modern banking customers could be given better tools to detect, respond to, and document card fraud in real time — before losses escalate and before evidence is lost.

The core thesis is that existing fraud-prevention systems are largely bank-side: they monitor transactions, apply risk models, and occasionally block or alert the customer after the fact. DaveTraceTech proposes a complementary, user-side framework that gives the account holder contextual awareness, immediate control, and a structured way to organise evidence — combining transaction monitoring, geolocation context, real-time alerts, emergency security controls, and evidence-led case management into a single, coherent experience.

This report presents the architecture, threat model, security considerations, and proposed technology stack for the concept. It is written for technical reviewers, placement officers, and potential collaborators who want to understand the thinking behind the project beyond what a landing page or GitHub repository can convey.

The report also demonstrates how principles from digital forensics — evidence integrity, chain of custody, structured documentation — can be applied to consumer-facing fraud response, bridging the gap between forensic methodology and everyday user experience.

02 — Problem Statement

Problem Statement

The gap DaveTraceTech targets across detection, response, and evidence.

The detection gap

Card fraud detection today is predominantly bank-side. Financial institutions use transaction monitoring systems, behavioural analytics, and risk-scoring engines to flag suspicious activity. However, these systems often operate with a delay — by the time a user is notified, the fraudulent transaction may have already completed, funds may have moved, and the window for immediate user-side intervention has closed.

The context gap

When users receive a fraud alert — whether via SMS, push notification, or banking app — the alert frequently lacks the context needed for the user to make a confident decision. A transaction amount, merchant name, and timestamp are often provided, but without location context, device information, or comparison against the user's normal behaviour, the user may dismiss a genuine alert or panic over a legitimate transaction.

The response gap

Even when a user identifies fraudulent activity, the tools available for immediate response are limited. Most banking apps allow card freezing, but the workflow is often buried in menus. There is rarely a single, rapid action that simultaneously freezes the card, logs the incident, notifies the bank's fraud team, and begins preserving evidence.

The evidence gap

When fraud does occur, the user is often left to gather evidence themselves — taking screenshots of transactions, saving emails, noting timestamps, and recalling phone conversations with support. This evidence is scattered across apps, emails, and memory. There is no structured, timestamped, tamper-evident record that the user can compile and share with their bank, police, or insurance provider.

DaveTraceTech addresses all four gaps by proposing a unified, user-facing system that brings detection, context, response, and evidence into a single workflow.

03 — Proposed Solution

Proposed Solution: Five-Pillar Framework

DaveTraceTech is structured around five interconnected pillars that form a complete fraud-response lifecycle.

01

Suspicious Transaction Detection

Real-time monitoring of transaction signals — amount anomalies, frequency spikes, unusual merchant categories, and deviation from established spending patterns — to flag potentially fraudulent activity.

02

Location and Context Comparison

Cross-referencing transaction location with the user's known or reported location. If a transaction occurs in London while the user's device reports Manchester, the system raises a location-mismatch alert with context.

03

Real-Time User Alerts

Context-rich push notifications that include the transaction details, location, merchant, and a risk assessment — enabling the user to make an informed decision rather than guessing.

04

Emergency Card Controls

One-tap emergency actions: freeze card, report lost or stolen, revoke trusted devices, and escalate to the bank's fraud team — all from a single interface with no menu navigation.

05

Evidence and Case Organisation

A structured case timeline that automatically logs alerts, user decisions, transaction metadata, timestamps, and supporting evidence — producing a chain-of-custody-ready record for investigation.

The proposed architecture flows from the user application through to the evidence vault and SOC dashboard.

The following diagram represents the proposed logical architecture of DaveTraceTech. Each layer has a specific responsibility in the fraud-response pipeline, from signal ingestion through to evidence preservation and administrative oversight.

The architecture is intentionally modular. Each layer can be developed, tested, and iterated independently. The Case Evidence Vault is the component most closely aligned with digital forensics principles — it is designed to maintain an immutable, timestamped record of every action taken during a fraud incident, supporting later investigation and potential legal proceedings.

05 — Core Components

Core Components

Detailed breakdown of each proposed component and its role in the fraud-response pipeline.

Transaction Monitoring Concept

The transaction monitoring component is designed to receive transaction events and evaluate them against a set of configurable rules. Proposed detection logic includes:

  • Amount threshold rules: Flag transactions exceeding a user-defined or dynamically calculated threshold based on historical spending.
  • Frequency analysis: Detect unusual clusters of transactions within a short time window that deviate from normal behaviour.
  • Merchant category monitoring: Flag transactions in high-risk merchant categories or merchants not previously associated with the user.
  • Velocity checks: Identify rapid successive transactions across different merchants or geographic locations.
  • Time-of-day analysis: Flag transactions occurring at unusual hours relative to the user's established patterns.

In the prototype, these rules are simulated using mock transaction data. A production system would integrate with banking APIs or payment processor webhooks.

Geolocation and Context Engine

The context engine compares transaction location data with the user's reported device location. The proposed workflow is:

  1. The user's device periodically reports its general location (with explicit consent).
  2. When a transaction event arrives, the system compares the transaction's merchant location with the user's last known location.
  3. If the distance exceeds a configurable threshold (e.g., a transaction in Edinburgh while the device reports London), a location-mismatch flag is raised.
  4. The alert includes both locations, the distance, and a risk indicator.

Location data is intentionally coarse — city or region level, not precise GPS coordinates — to balance fraud-detection value with privacy minimisation.

Risk Scoring Logic

Each transaction event is assigned a composite risk score based on weighted factors:

  • Amount anomaly — how far the transaction amount deviates from the user's average.
  • Location mismatch — distance between transaction and user device location.
  • Frequency deviation — whether the transaction is part of an unusual cluster.
  • Merchant familiarity — whether the merchant has been transacted with before.
  • Time deviation — whether the transaction falls outside the user's typical active hours.

The risk score drives the alert priority: low, moderate, high, or critical. High and critical alerts trigger immediate push notifications with emergency control options.

Alert and Verification Flow

When a transaction is flagged, the alert engine generates a notification containing:

  • Transaction amount, merchant, and timestamp
  • Transaction location and distance from user device
  • Risk score and contributing factors
  • Two primary actions: "This was me" (dismiss) or "This was not me" (escalate)

Selecting "This was not me" triggers the emergency control workflow and opens a new case in the evidence vault.

Emergency Lockdown and Freeze Workflow

The emergency control workflow is designed to execute multiple actions from a single user interaction:

  1. Freeze the card — prevent further transactions (simulated in prototype).
  2. Log the incident — create a timestamped case entry in the evidence vault.
  3. Flag for bank review — queue the case for the bank's fraud team (conceptual).
  4. Preserve evidence — capture the alert context, transaction metadata, and user decision into the case timeline.
  5. Provide guidance — display next steps: contact bank, report to Action Fraud, change passwords, monitor accounts.

Evidence Chain and Case Timeline

The evidence vault is designed as an append-only log — once an entry is written, it cannot be modified or deleted. Each entry includes:

  • Timestamp (UTC, ISO 8601)
  • Event type (alert, user decision, card freeze, evidence upload, case note)
  • Transaction metadata (amount, merchant, location, reference)
  • User-submitted evidence (screenshots, notes, reference numbers)
  • Action taken and by whom

This structure mirrors digital forensics chain-of-custody principles, adapted for a consumer-facing application.

User Fraud-Awareness Guidance

Beyond technical controls, DaveTraceTech proposes embedded educational content — short, contextual guidance displayed at the point of decision. For example, when a user dismisses a high-risk alert, the system could display a brief reminder of what to watch for. This turns the fraud-response experience into a learning opportunity rather than a friction point.

06 — Threat Model

Threat Model

Threats DaveTraceTech is designed to address, and the proposed controls for each.

A security-focused system must account for the threats it is designed to mitigate and those it must defend against as a platform itself. The table below outlines the primary threats and the DaveTraceTech controls that address them.

ThreatRisk DescriptionDaveTraceTech Control
Stolen or cloned card Attacker uses stolen card details for in-person or online transactions. Transaction monitoring + location mismatch + rapid freeze
Account takeover Attacker gains access to the user's banking account and authorises transactions. Device trust verification + anomaly detection + emergency device revocation
SIM-swap fraud Attacker hijacks the user's phone number to intercept SMS authentication. Multi-channel alerts (push + email) + device-based authentication
Phishing-assisted fraud User is tricked into authorising a transaction or revealing credentials. Contextual alerts + fraud-awareness guidance + verification prompts
Social engineering Attacker manipulates the user into dismissing a legitimate alert. Risk-score display + contextual guidance + "Are you sure?" verification on high-risk dismissals
False positives Legitimate transactions are flagged, causing user fatigue and alert dismissal. Adaptive thresholds + user feedback loop + risk-score transparency
Malicious insider Authorised staff member accesses or alters case evidence. Role-based access control + immutable audit log + access logging
Data leakage Sensitive transaction or location data is exposed. Encryption at rest and in transit + minimal data collection + no full card number storage

Threat modelling for DaveTraceTech follows the principle that the system itself must be resilient — it is not enough to detect fraud in the user's account if the platform can be compromised, manipulated, or used to phish the user further.

07 — Security and Privacy

Security and Privacy Considerations

Design principles that govern how DaveTraceTech would handle data, access, and compliance.

Data protection principles

  • Encryption at rest: All stored transaction data, evidence, and case records are encrypted using industry-standard algorithms (e.g., AES-256).
  • Encryption in transit: All communication between the user application, signal layer, and backend uses TLS 1.2 or higher.
  • No full card number storage: DaveTraceTech never stores full card numbers. Only the last four digits and a tokenised reference are retained for display purposes.
  • Minimal data collection: Location data is collected at city/region granularity only, with explicit user consent, and retained only for the active fraud window.

Access control

  • Role-based access control (RBAC): Users, support staff, and administrators have distinct permission sets. Only authorised staff can access the SOC dashboard or case evidence vault.
  • Multi-factor authentication: All administrative access requires MFA. User-side emergency actions may require biometric or PIN re-authentication.
  • Audit logging: Every access to case evidence, every administrative action, and every system configuration change is logged with timestamp, actor, and action.

Privacy and compliance

  • GDPR awareness: The system is designed with data-minimisation, purpose-limitation, and user-rights principles in mind. Users can view, export, and request deletion of their case data.
  • Consent for location use: Location services require explicit opt-in. Users can disable location reporting at any time, with a clear explanation of the trade-off (reduced fraud-detection accuracy).
  • Data retention: Case evidence is retained for a defined period (e.g., 90 days post-resolution) and then automatically purged, unless the user or legal process requires extension.

Evidence integrity

  • Append-only evidence log: Case entries cannot be edited or deleted once written, ensuring the integrity of the evidence timeline.
  • Cryptographic hashing: Each evidence entry is hashed, and the hash chain links consecutive entries — enabling tamper detection if any record is altered.
  • UTC timestamping: All events use ISO 8601 UTC timestamps to avoid timezone ambiguity in cross-jurisdictional investigations.
08 — Evidence Handling

Evidence Handling and Case Management

How DaveTraceTech applies digital forensics principles to consumer fraud response.

The evidence handling component of DaveTraceTech is where the project most directly intersects with digital forensics methodology. Traditional digital forensics follows a structured process: identification, preservation, collection, examination, analysis, and reporting. DaveTraceTech adapts this process for the consumer fraud-response context.

Case timeline structure

Each fraud incident is represented as a case — a chronological timeline of events. A typical case might include:

  1. Alert generated — Transaction flagged, risk score calculated, alert sent to user.
  2. User decision — User confirms "This was not me" and triggers emergency controls.
  3. Card frozen — Emergency freeze executed, timestamp logged.
  4. Evidence captured — Transaction metadata, alert context, and device information automatically written to the case.
  5. User adds evidence — User uploads a screenshot of a phishing email, adds a note about a suspicious phone call, or references a bank reference number.
  6. Case escalated — Case flagged for bank fraud team review (conceptual).
  7. Case resolved — Outcome recorded, case archived with full timeline preserved.

Forensic integrity measures

  • Hash chaining: Each evidence entry includes a hash of its content and the hash of the previous entry, creating a tamper-evident chain. Any modification to a historical entry breaks the chain.
  • Immutable storage: Once written, evidence entries are stored in an append-only data structure — they cannot be modified through the application interface.
  • Complete audit trail: Every user action, system action, and administrative action is logged with actor identity, timestamp, and action details.

Export and sharing

Users can export a complete case file — a structured document containing the full timeline, evidence references, and metadata — in a format suitable for sharing with their bank, Action Fraud, or legal representatives. The export includes the hash chain for integrity verification.

This approach brings professional-grade evidence handling to the consumer context, making it easier for users to present a clear, structured, and verifiable account of what happened — rather than relying on memory, scattered screenshots, and approximate timestamps.

10 — Limitations

Limitations and Open Challenges

Honest assessment of what DaveTraceTech cannot yet do and the challenges it faces.

  • Banking API dependency: Real-time transaction monitoring requires integration with banking or payment processor APIs. DaveTraceTech currently simulates transaction events — a production system would require partnerships and compliance with financial regulations such as PSD2.
  • False positive management: Fraud-detection systems must balance sensitivity against user friction. Excessive false positives lead to alert fatigue; excessive false negatives leave users exposed. The risk-scoring model would require extensive tuning with real (anonymised) data.
  • Compliance and regulatory review: Any system handling transaction data, user location, and fraud evidence must undergo legal and compliance review — including GDPR data protection impact assessment, PCI DSS considerations, and potentially FCA guidance.
  • Authentication security: The emergency controls are only as secure as the authentication protecting them. If an attacker can compromise the user's authentication, they could use the emergency controls maliciously — or suppress legitimate alerts.
  • Evidence legal admissibility: While the hash-chained evidence log is designed for forensic integrity, its admissibility in legal proceedings would depend on the jurisdiction, the implementation's certification, and the broader system's security posture.
  • Scalability: Real-time transaction monitoring at scale — processing thousands of events per second across many users — presents significant engineering challenges in terms of latency, throughput, and reliability.
  • User adoption: The system's effectiveness depends on users enabling location services, responding to alerts promptly, and engaging with the evidence features. Designing for adoption without creating security fatigue is an ongoing UX challenge.

Documenting these limitations is itself a security practice — it demonstrates awareness of the system's boundaries and the work required to move from concept to production.

12 — Conclusion

Conclusion

DaveTraceTech represents a convergence of cybersecurity, digital forensics, and user-centred design. It asks a practical question: what if the tools used to investigate fraud after the fact could be placed in the hands of users during the incident itself?

The project demonstrates an architectural approach to a real-world problem — combining transaction monitoring, location context, real-time alerts, emergency controls, and forensic-grade evidence handling into a single, coherent system. While the current implementation is a prototype, the design thinking, threat modelling, and security considerations presented in this report reflect the depth of analysis that a production system would require.

DaveTraceTech also illustrates how David Aguoru's background in cyber security and digital forensics, combined with his MSc study in network and information security, informs a practical, evidence-led approach to technology building. The project is not just a concept — it is a demonstration of how security thinking can shape product design from the ground up.

The next steps are technical: refining the prototype, implementing the risk-scoring demo, building the case timeline, and conducting a formal security review. The vision remains clear — giving people better tools to detect, respond to, and document fraud, at the moment it matters most.
